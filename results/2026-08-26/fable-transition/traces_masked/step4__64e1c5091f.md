## Verdict: syntactically fine, but not production-safe as written

"Looked correct locally" is exactly the trap here: every statement produces the right rows on a small table. The problems are all about **locking, duration, and data semantics**, and none of them show up until `orders` is large and under live traffic.

### 1. The three statements likely run in one transaction → sustained exclusive lock (most serious)

Most migration runners (Rails, Alembic, Flyway on Postgres, Knex, Prisma) wrap a migration file in a single transaction. On Postgres, `ALTER TABLE ... ADD COLUMN` takes an `ACCESS EXCLUSIVE` lock, and that lock is **held until the transaction commits** — i.e. through the index build *and* the full-table `UPDATE`. Every read and write to `orders` blocks for the entire backfill. On a busy orders table that's an outage, not a migration.

Worse: if any long-running query already holds a lock on `orders`, the `ALTER` queues behind it, and every subsequent query queues behind the `ALTER`. Set a `lock_timeout` (e.g. `SET lock_timeout = '5s'`) so the migration fails fast instead of pile-driving the app.

### 2. `CREATE INDEX` without `CONCURRENTLY` blocks writes for the whole build

Plain `CREATE INDEX` on Postgres takes a `SHARE` lock — reads proceed, but all `INSERT/UPDATE/DELETE` on `orders` block until the index is built. Use `CREATE INDEX CONCURRENTLY`, which **cannot run inside a transaction block** — so this statement has to live in its own migration with transactions disabled (`disable_ddl_transaction!` in Rails, `atomic = False` in Django, `-- +goose NO TRANSACTION`, etc.).

Also, the order is backwards: building the index *before* the `UPDATE` means every backfilled row must also update the index. Backfill first, index last.

### 3. Single-statement `UPDATE` across the whole table

`UPDATE orders SET status = 'fulfilled' WHERE shipped_at IS NOT NULL` will touch most of the table in one shot (for a mature shop, the majority of orders have shipped). Consequences at scale:

- Row locks held on every matched row until commit → conflicts with the app updating those same orders.
- Postgres MVCC: each updated row leaves a dead tuple. Rewriting most of the table roughly doubles its on-disk size until vacuum catches up.
- A huge WAL burst → replication lag on replicas, potentially minutes.
- If it fails or is cancelled at 90%, the whole thing rolls back.

Batch it by primary key range (e.g. 5–10k rows per statement, committing between batches, sleeping briefly), ideally as a script outside the DDL migration.

### 4. Data semantics — is "not shipped ⇒ pending" actually true? (check this one with the business logic)

After this migration, **every** row without a `shipped_at` is `'pending'`, including orders that are cancelled, refunded, failed payment, or years-old and abandoned. And every shipped order is `'fulfilled'` even if it was returned. If `orders` has columns like `cancelled_at`, `refunded_at`, or `payment_status`, the backfill needs cases for them. Mislabelling old dead orders as `pending` is the kind of bug that surfaces as a support ticket, not a stack trace.

### 5. Race between backfill and app deploy

Any order that ships between the `UPDATE` running and the new app code (that writes `status` on ship) being deployed stays `'pending'` forever. Either deploy app code that writes `status` *before* the backfill, or make the backfill idempotent and re-run it after deploy.

### 6. Engine-dependent cost of the `ADD COLUMN` itself

- Postgres ≥ 11: metadata-only for a constant default — fast. Postgres < 11: full table rewrite.
- MySQL 8 InnoDB: `ALGORITHM=INSTANT` if appended — fast. MySQL 5.7: in-place rebuild, long on big tables.

Confirm engine and version before assuming this step is cheap.

### Minor

- `VARCHAR(20)` with no `CHECK` constraint or enum means any string is accepted; consider `CHECK (status IN ('pending','fulfilled',...))` — added as `NOT VALID` then validated separately on Postgres to avoid a scan under lock.
- A single-column index on a low-cardinality status column is often ignored by the planner. If the real query is "find unfulfilled orders," a partial index (`WHERE status <> 'fulfilled'`) is smaller and actually used.
- No down migration.
