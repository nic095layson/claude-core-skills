## Where to start: not with the code

The first step of a session→JWT migration is a **written plan that answers four questions**, because the answers change the design more than any code detail does:

1. **What does a session hold today?** Just a user ID, or mutable state (cart, CSRF token, impersonation, feature flags, MFA step)? Anything mutable can't live in a JWT — it needs a different home (DB, cache, or a short-lived token + refresh).
2. **Do you need revocation?** "Log out everywhere," admin ban, password change → invalidate. Stateless JWTs can't do this. The usual answer is short-lived access tokens (5–15 min) + a stored, revocable refresh token — which means you're *not* fully stateless, and that's fine and expected.
3. **Who are the clients?** Browser-only (cookies, `HttpOnly`, `SameSite`, and CSRF still matter — JWT doesn't remove that), mobile/SPAs (bearer header), or third-party services (this is where JWT actually earns its keep)?
4. **Why?** Horizontal scaling, service-to-service auth, a mobile client, or dropping Redis? The reason determines whether you need JWT at all or just a different session store.

## Phased plan (assuming the common answers: browser + API clients, revocation required)

| Phase | Work | Success criterion |
|---|---|---|
| **0. Inventory** | Grep for every session read/write (`req.session`, `session[...]`, `@login_required`, etc.); catalogue every key stored in the session and every consumer | A table of session keys → owner → mutability. Nothing else starts until this exists. |
| **1. Seam** | Introduce an `AuthContext` / `getCurrentUser()` abstraction; route all consumers through it while it's still backed by sessions | All tests green, zero behavior change, no direct session access outside the auth module |
| **2. Token issuance** | Add JWT sign/verify (RS256/ES256, key rotation via `kid`, `iss`/`aud`/`exp` claims) + refresh-token table; issue tokens *alongside* sessions | Login produces both; nothing consumes the JWT yet |
| **3. Dual-read** | Auth middleware accepts either a valid session or a valid JWT | Existing users stay logged in; new logins work with cookies cleared |
| **4. Cutover** | Flip issuance to JWT-only; stop writing sessions | Session store write volume → 0 |
| **5. Remove** | Delete session middleware and store after max session TTL elapses | No session code remains; revocation, logout-everywhere, and password-change invalidation all verified end-to-end |

Phase 1 is where the real leverage is: once every consumer goes through a seam, the rest is contained inside the auth module and can ship incrementally instead of as a big-bang PR.

## Things people get bitten by
- **Token in `localStorage`** → XSS = account takeover. Use `HttpOnly` cookies for browsers; then CSRF protection stays.
- **`alg: none` / HS256 with a public-key confusion** — pin the algorithm in the verifier.
- **Fat tokens** — putting roles/permissions in the JWT means they're stale until expiry. Keep claims minimal; look up authorization server-side.
- **Clock skew** across services — allow a small leeway on `exp`/`nbf`.
- **Migration window** — users mid-session during cutover; dual-read (phase 3) is what prevents a mass logout.
