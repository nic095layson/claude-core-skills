## Verdict: syntactically fine, but not production-safe as written

"Ran correctly locally" verifies two things: the syntax parses and the mapping is right *for your local data*. It says nothing about the two things that actually bite in production — lock behavior at scale and edge-case rows you don't have locally.

### 1. Correctness: the backfill mapping is probably too coarse (highest priority)

The logic is binary: `shipped_at IS NOT NULL → 'fulfilled'`, everything else → `'pending'`. That silently mislabels any row that's neither:

- Cancelled / refunded / failed-payment orders with no `shipped_at` → become `'pending'`
- Orders shipped and later returned or refunded → become `'fulfilled'`
- Orders delivered (if you track `delivered_at`) → `'fulfilled'` may or may not be the right terminal state

If `orders` has any of `cancelled_at`, `refunded_at`, `delivered_at`, `returned_at`, `payment_status`, etc., the backfill needs a `CASE` that maps them, and the untouched remainder should be inspected before you call it `'pending'`. Check before running:

```sql
SELECT count(*) FROM orders WHERE shipped_at IS NULL;  -- are these really all "pending"?
```

If the table genuinely only has `shipped_at` as a state signal, this finding drops away — but I can't confirm that from here.

### 2. Locking: as written this can take `orders` offline

- **`UPDATE` with no batching** rewrites every row in one transaction. On Postgres that doubles the table's on-disk size until vacuum and holds row locks to commit; on MySQL InnoDB it fills the undo log and, if you replicate, ships one giant transaction that stalls replicas.
- **If your migration runner wraps the file in a transaction** (Flyway, Alembic, Rails, Django, Knex all do on Postgres by default), the `ACCESS EXCLUSIVE` lock from the `ALTER` is held for the *entire duration of the UPDATE*. Reads and writes to `orders` block until the backfill finishes.
- **`CREATE INDEX` without `CONCURRENTLY`** (Postgres) takes a `SHARE` lock that blocks all inserts/updates/deletes for the build. On MySQL InnoDB it's online by default; on SQL Server it's offline unless `ONLINE = ON` (Enterprise).
- `ALTER TABLE ... ADD COLUMN ... DEFAULT 'pending'` itself is cheap on Postgres ≥ 11 and MySQL ≥ 8.0.12 (metadata-only). On Postgres ≤ 10 it rewrites the whole table under an exclusive lock.

### 3. Ordering: index before backfill is backwards

Creating the index *before* the `UPDATE` means every row update also maintains the index — slower backfill, more WAL, and on Postgres a bloated index. Backfill first, then index.

### 4. Deploy-ordering race

Between the `UPDATE` finishing and the application starting to write `status`, any order that ships gets stuck at `'pending'`. Either deploy the app code that writes `status` first (the column default keeps it safe), or run a second catch-up `UPDATE` after the deploy.

- `VARCHAR(20)` with no `CHECK` / enum — any string is accepted. Worth adding once the value set is settled.
- A plain index on a low-cardinality status column is only useful for querying the minority value; if most rows are `'fulfilled'` and you query for `'pending'`, a partial index (`WHERE status <> 'fulfilled'`, Postgres) is much smaller.
